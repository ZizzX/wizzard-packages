A flow is a definition: the order of steps, the conditions that include them, and the
validation that guards them. The engine reads that definition; your components render whatever
step it says the flow is on. Below is the whole of that, running, in about two minutes.

## Install

Pick the binding you render with. The choice is remembered, here and on every other page.

### In an app you already have

The `@canary` tag is where v1 lives until the 1.0.0 release; it moves to `latest` then.

Supported: Node 20.11 or newer, TypeScript 5 or newer, React 18 or newer, Vue 3.5 or newer.
Every package ships ESM and CJS, with types for both. `react` and `react-dom` are peer
dependencies of the React binding and `vue` of the Vue one; `core` depends on nothing.

## The flow

A definition does more than order two steps. This one branches, guards a step with a named
validator, and sends Back somewhere other than where it came from. It takes three files: the
definition, the code it names, and the place the two are put together and driven. They go in
`src/branching/`, so they sit beside the quickstart's files rather than over them.

### 1. The definition

<Code code={branchingFlowSource} lang="ts" title="src/branching/flow.ts" />

Three things are true of this object before any of your code runs. `company` is part of the flow
only while `details.payer` is `business`: `when` is evaluated against the data as it is now, so
changing the answer adds or removes the step. `details` cannot be left until the validator named
`needsEmail` lets it. And Back from `payment` lands on `details`, not on whatever came before it.

Each `step<T>()` declares what that step writes into `data`, under the step's id - `details`
writes `data.details.email` and `data.details.payer` - which is why `when` reads
`data.details.payer`. `step` returns the object it is given; the type is for the compiler only.

### 2. The code the definition names

<Code code={branchingRegistrySource} lang="ts" title="src/branching/registry.ts" />

The definition stays JSON, so it cannot hold a function. It holds the name `needsEmail`, and the
registry holds the function under that name. The engine joins them when it validates the step.

A validator answers with the problems it found, as messages keyed by field, or with `null` when
the step may be left. It does not answer `true` or `false`: only an object with at least one key
refuses the move, so a validator that returns `false` lets every move through and has no message
to show. [Validation](../validation/) has the whole contract.

### 3. Creating and driving the wizard

<Code code={branchingRunSource} lang="ts" title="src/branching/run.ts" />

`createWizard` takes the definition and the registry and returns the engine. It is created idle,
on no step. `start()` enters the first step, and from then on the engine moves only when it is
asked to. In this file every call is made by hand. In an app, a binding's provider creates the
wizard and calls `start()` when it mounts, and your components call `set` from inputs and `next`
and `back` from buttons. `destroy()` is the owner's last call: it aborts every move still running,
removes the listeners and runs each plugin's teardown. A provider that created the wizard makes
that call on unmount. A wizard you created yourself, here or handed to a provider, is yours to
destroy when you are done with it.

To run it in the app from [In a new app](#in-a-new-app), add `import './branching/run';` to
`src/main.ts` - `src/main.tsx` in React - and start `pnpm dev`. The script prints to the browser
console:

<Code code={branchingOutput} lang="text" title="Output" />

Each line is one claim from the definition. The first `next()` is refused with the validator's
message, and the message is kept in `state.errors` under the step's id. With a business payer
Next goes to `company`. Back from `payment` skips `company`, because of `on.back`. Once the payer
is `personal`, Next skips `company`, because its `when` no longer holds. A test in the repository
runs this script and compares what it prints with the block above, so the output cannot fall out
of date.

[The flow](../flow/) is the shape of that object in full - every field, and the two of them

`when` is written in. [Navigation](../navigation/) covers moving through a flow and the
refusals a move can return instead. [Validation](../validation/) separates checking a
definition from checking a user's answers, and [Persistence](../persistence/) covers writing a
session out and refusing to restore one that no longer fits.

[Concepts and glossary](../concepts/) defines every word those pages are written in, once, and
[What you can build](../showcase/) puts branching, a repeat, a sub-flow, a loading step and a
restored session into one definition. Every export, with its signature, is in the
