[Getting started](../start/) is one screen, and [What you can build](../showcase/) is a finished
flow you read rather than build. This page is the road between them: a conference registration
that starts as two steps and grows, one change at a time, into a wizard with validation, a
branch, a list of guests, a step that loads, a session that survives a reload and a plugin you
wrote.

Every step changes a file or two and adds a short script that drives the wizard and prints what
the change made work. A file that already existed is shown as the change to it, so what you type
is the difference. The code and the output on this page are read from files in the repository,
and a test runs every script and compares what it prints, so a line here cannot say something
the engine does not do.

The scripts need `@wizzard-packages/core` - install it as [Getting started](../start/#install)
shows - and a way to run TypeScript, such as `npx tsx run.ts`. Step 6 adds the plugins package.
The browser comes in at the end.

## 1. Two steps and a review

A flow is data: the order of the steps and what each one is. `step<T>` names the shape of the
answers a step collects, which is what lets `set` and `get` check them; the object it returns is
still plain JSON.

Nothing is current until `start()` enters the first step. `back()` moves, and it does not throw
away what was typed on the step it returns to. `active` is the route from start to end, worked
out from the flow rather than stored.

A refused `next()` is a value with a `reason` and the messages, not an exception, and the wizard

## 3. A step for some tickets only

A business ticket needs a company name; a standard one does not. `when` puts a step on the route
only while an expression holds, and the expression is data too - `eq(get(...), ...)` builds it.

<TutorialFile step="03-branch" file="flow.ts" />

<TutorialFile step="03-branch" file="run.ts" />

<TutorialFile step="03-branch" file="run.out.txt" />

The route is worked out from the answers on every read, so changing the ticket changes the steps
ahead without anything being told to recompute. With a standard ticket `next()` from `ticket`
lands on `review`; with a business one it lands on `company`. What the person typed on a step
that then goes off the route stays in the data;
[Clear abandoned branch data](../clear-abandoned-branch-data/) is how to decide what does not.

## 4. The same questions for every guest

A ticket can bring guests, and each guest is asked the same two things. That is a flow of its
own, `guest`, run once per item of a list by a `group` with a `repeat`.

<TutorialFile step="04-repeat" file="flow.ts" />

Three fields beside the group are not optional. `keyBy` names what tells one guest from another,
so a guest keeps their answers when the list is edited. The group's `when` has to say what
happens while the list is empty ([`repeat-without-when`](../../errors/repeat-without-when/)), and
a flow with a repeat carries a `version`
([`repeat-without-version`](../../errors/repeat-without-version/)), because a saved session
names guests of a list that may have changed shape since.

Walking into a group is a separate entry point, so a flow without one does not pay for it:

<TutorialFile step="04-repeat" file="wizard.ts" />

<TutorialFile step="04-repeat" file="run.ts" />

<TutorialFile step="04-repeat" file="run.out.txt" />

Where the wizard is, inside a group, is a stack: the group with the guest's key, then the step of
the guest's flow. The engine does not decide where a guest's answers are kept; a path with the
guest's key in it, `guests.g1.diet`, keeps them apart. [Groups, repeat and
sub-flows](../groups/) covers the rest - what a nested flow can read about its item, and
`back()` across a group's edge.

## 5. A step that waits for its data

The sessions a person can pick come from a server. `load` names a resolver the move waits on, so
no move makes the step current with nothing to pick from.

<TutorialFile step="05-load" file="flow.ts" />

`load` gates the step and discards what the resolver returns, so the resolver puts the answer
where the page will read it - here a module, in an app a store or a query cache.

<TutorialFile step="05-load" file="registry.ts" />

<TutorialFile step="05-load" file="run.ts" />

<TutorialFile step="05-load" file="run.out.txt" />

While the agenda loads the wizard reports itself busy, which is what the buttons of the rendered
wizard below are disabled on, and no commit ever shows `sessions` current before the talks are in.
[Loading a step](../async-steps/) covers a load that fails and one that is overtaken by another
move.

## 6. Keep the session across a reload

The `persist` plugin writes the session on every change and reads it back when the wizard starts.
It ships in its own package, beside the engine:

<Code code={installPlugins} lang="bash" />

In a browser it uses `localStorage`; the script hands it a `Map` behind the same three methods, so
a reload can happen in one process.

<TutorialFile step="06-save" file="wizard.ts" />

<TutorialFile step="06-save" file="run.ts" />

<TutorialFile step="06-save" file="run.out.txt" />

`onRestore` is told once, at start, whether a session came back and, when one did not, why - here
`persist/nothing-stored` on the first visit. Writes are coalesced, and `destroy()` flushes the
last one, as closing the page does in a browser. [Restore after reload](../restore-after-reload/)
is this step rendered, and [Persistence](../persistence/) is the format underneath.

A restore puts the wizard back on its step before `start()`, and `start()` enters a step that
loads again, in place: a page reloaded on `sessions` fetches the agenda step 5 loads before the
step reads as ready, and `back()` still goes where it went before the reload.

## 7. A plugin of your own

`persist` is a plugin, and nothing about it is privileged: a plugin is an object with a name and
the hooks it needs. This one reports every step a move lands on, which is the shape of an
analytics event.

The refused `next()` is not in the trail: `afterNavigate` runs once a move has committed, so it
sees only moves that happened, and it cannot undo one. A session `persist` restores is not a
move either: the wizard below, reloaded, does not list the step it came back on - unless that
is `sessions`, which it enters again to fetch the agenda. A plugin that must stop a move refuses it from `beforeNavigate`.
[Writing a plugin](../plugins/) lists every hook and the order they run in.
