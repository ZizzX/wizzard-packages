Hooks

The engine is the same object in both bindings. A binding does one job: put that object where components can reach it, and turn its snapshot into something the framework re-renders on. The hook names are identical across React and Vue; what differs is what they hand back, because a React hook returns a value and a Vue composable returns a ref.

Providing the wizard

Section titled “Providing the wizard”
  • React
  • Vue

WizardProvider takes the options of createWizard - flow, registry, plugins, data, ctx, state, groups, subFlows - and builds the engine itself, or takes an engine you built with wizard. Passing both throws provider-wizard-and-options: options beside a built engine would be silently ignored.

provideWizard takes the options of createWizard - flow, registry, plugins, data, ctx, state, groups, subFlows - and builds the engine, or takes an engine you built and provides that one. An engine it created is destroyed with the scope, so plugin teardown runs; one you passed in stays yours to destroy.

Each is what its framework expects - a component in React, a setup function in Vue - and that asymmetry is deliberate. Everything below it is the same in both.

The wizard is started on mount. If that first move throws, which a first step whose loader rejects will do, there is no caller to throw to: the binding logs start-failed with the cause and no step is current. The wizard has not started, so useWizard().start() runs the first move again - from a retry button - and so does mounting again.

On the server, mount never runs. A wizard rendered by SSR navigates nowhere and hydrates into its first step on the client.

The hooks

Section titled “The hooks”

Each one is a narrower view of the same snapshot. Take the narrowest that answers the question: a component that reads one field re-renders when that field changes, and one that reads the whole snapshot re-renders on every commit.

Hook React returns Vue returns
useStep() current, index, isFirst, isLast, progress, breadcrumbs, active, status the same fields, each a ComputedRef
useNavigation() next, back, go, cancel, and canBack, isBusy, isLast as booleans the same methods, and the three flags as ComputedRefs
useField<T>(path) [value, setValue] a WritableComputedRef, for v-model
useErrors(stepId?) the error map of a step, or of the current one that map as a ComputedRef
useWizardSelector(fn, isEqual?) one derived value one derived value as a ComputedRef
useWizardSnapshot() the whole snapshot the snapshot as a Ref
useWizard() the engine the engine
useOptionalWizard() the engine, or null outside a provider the same

Drawing a step

Section titled “Drawing a step”

useStep is what a stepper needs and nothing else. It compares its fields one by one, including the status of each breadcrumb, so a step turning invalid repaints the stepper.

  • React
  • Vue

Each field is a ComputedRef, so destructuring keeps it reactive - unlike destructuring a reactive object.

Moving

Section titled “Moving”

useNavigation hands back the engine’s four moves unchanged and the three flags a set of buttons needs. Navigation is async and returns a result, not a boolean: await next() gives { ok: false, reason: 'blocked', by: 'age-check' } when a guard refuses. Navigation has the full list of refusals.

Reading and writing a field

Section titled “Reading and writing a field”

useField addresses the same dot paths the flow does, so data.trip.name in an expression is 'trip.name' here.

  • React
  • Vue

Errors

Section titled “Errors”

useErrors() reads the messages of the current step, useErrors('payment') those of a named one. The map is the one validation produced, so a field component does not need the result of the call that created it. Render field errors is the whole pattern.

One derived value

Section titled “One derived value”

useWizardSelector is the escape hatch for anything the hooks above do not cover, and the way to keep a large tree from re-rendering on every commit:

In React it takes a second argument, an equality function, which defaults to Object.is. Give it one when the selector returns a fresh object each time, or the component re-renders on every commit. Vue has no such argument: the ComputedRef is recomputed once per commit, so a selector building a fresh object hands its watchers a new identity each time. Select a primitive, or compare in the watcher.

The engine itself

Section titled “The engine itself”

useWizard() is the engine: set, get, validate, setErrors, watch, select, subscribe, batch, patchFlow and the rest. Typing it against a flow - useWizard<typeof signup>() - types go, get and set against that flow’s steps and data.

Outside a provider useWizard() and every hook built on it throw provider-missing. useOptionalWizard() returns null there instead, which is what a component rendered both inside and outside a wizard needs - a diagnostic panel, say, which should report that it has nothing to watch rather than crash the application it is watching.

Owning the engine yourself

Section titled “Owning the engine yourself”

The provider builds the engine by default, but it does not have to. Hand it one you built and the object is yours: it exists before the tree mounts, it survives the tree unmounting, and destroy() is never called for you - the binding disposes only an engine it created itself.

  • React
  • Vue

One thing the binding still does with an engine you passed: it starts it on mount, because a wizard with an empty stack has no step to render. start() is idempotent, so a wizard you already started is left where it is.

Reach for this when the wizard has to outlive the components that show it - a flow that continues across routes, one built from a server response before anything renders, or a test that drives the engine directly and mounts a component to look at it.

Without a provider at all

Section titled “Without a provider at all”

The hooks read the wizard from React context or Vue’s injection, and there is no argument that passes one in: outside a provider they throw. The engine itself needs neither. It is an external store - subscribe returns an unsubscribe, and getSnapshot returns the same object until a commit - so a component can read one directly with what its framework already has. Three things have to happen, and with no provider each of them is yours: create the engine, start it, and destroy it when it is no longer needed.

  • React
  • Vue

1. Create the engine where it should live. A module-level engine is one wizard for the whole page, shared by every component that imports it, and it lives until the page is gone - which is why nothing here calls destroy().

2. Subscribe to it. useSyncExternalStore is the whole bridge. The third argument is the server snapshot, and passing the same getSnapshot is right because the engine has not started there: the server renders the empty state and the client hydrates into it.

It takes the engine rather than importing one, so the same bridge works for the module-level wizard above and for a wizard owned by one screen, below. A wizard that changes re-subscribes, because subscribe is a new function then.

3. Start it, and render. start() is what enters the first step - without it current is null and there is nothing to draw. It is idempotent and asynchronous, it must not run on the server, and it rejects when the first step’s loader fails, so it goes in an effect with a catch. This is the part the provider does for you.

When the wizard belongs to one screen rather than the page, it is created in useState so a re-render does not build a second one, destroyed in the effect’s cleanup - a plugin’s teardown runs there, and an engine nobody destroys keeps its subscriptions - and rebuilt when it has been destroyed. That last branch is for StrictMode, which in development mounts, unmounts and mounts again while useState keeps the same value: without it the second mount is handed a torn-down engine, and start() does not bring one back. WizardProvider carries the same three lines, which is the clearest argument for using it instead.

That is what a provider is: those three responsibilities plus the context that carries the engine to components you did not pass it to. Taking them on by hand costs about twenty lines and the hooks above stop working, so reach for this only when context genuinely cannot be used - a wizard read from outside the component tree, or one component watching two wizards at once.
